# 引导式需求采集引擎

> 读取时机：Phase 0 开始前。本文档是引导式问答的**唯一权威**（SKILL.md 仅保留流程骨架），定义了准入判断、完整问答逻辑、话术、分支规则和防跑偏机制。

---

## 设计原则

1. **选择优于描述** — 用户选比用户写容易 10 倍
2. **示例锚定** — 每个填空题旁边必须有高质量示例，用户照着改比从零写容易 5 倍
3. **回显确认** — 用户不擅长判断"我说得对不对"，但擅长判断"你理解得对不对"
4. **渐进深入** — 先粗后细，先选择后填空，先核心后边界
5. **容错降级** — 用户跳过的信息用默认值兜底，不阻塞流程
6. **每问附推荐** — 每道选择题标注一个推荐选项（按同类 skill 高频分布给出，加 ⭐ 标记），每个填空题的示例即推荐答案；用户判断一个现成答案比组织语言容易（纪律：推荐只是推荐，决策是用户的）

---

## 第零层：准入判断（运行时守卫）

进入引导前，先用一句话判断用户意图，避免误入流程。本表是准入路由的唯一权威：

| 用户意图 | 识别信号 | 处理 |
|---------|---------|------|
| 检查/评估现有 skill | "检查"、"有没有问题"、"评估"、"打分" | 不进入，**照抄拒绝话术模板**（见下）路由：检查用 skill linter，评估优化用 `skill-eval-optimizer` |
| 小修改现有 skill | "改一下"、"加个触发词"、"调整描述" | 不进入，照抄拒绝话术模板，提示：直接编辑对应 `SKILL.md` 即可 |
| 疑似已有同类 skill | 扫描已安装 skill 目录命中同类能力 | **停等用户裁决**（复用裁决话术见下），裁决「确认新建」才进入第一层 |
| 范围过大（≥3 类能力） | 一句话里塞了查询+生成+通知+对账等多类 | 引导聚焦："一个 skill 聚焦一件事，你最常用/最痛的是哪个？先做它，其余可后续拆分" |
| 正常创建单一 skill | 其余情况 | 进入第一层 |

**拒绝话术模板（Step 0.0 命中非创建行时照抄，不自由发挥、不展开帮忙做事）**：

> 本 skill 仅负责创建新 skill，不处理这类请求：
> - 检查/规范审查 → 使用 skill linter（结构规范检查工具）
> - 评估/打分/优化已有 skill → 使用 `skill-eval-optimizer`
> - 小修改 → 直接编辑对应 `SKILL.md` 即可

**复用裁决话术（Step 0.0.5 命中疑似同类 skill 时照抄，三选项停等）**：

> 扫描到你机器上可能已有同类 skill：`{skill-name}`（{一句话能力对比}）。为避免重复造轮子，请先选择：
> - A ⭐ 先试用现有的（我给你一条可直接粘贴的试用指令）
> - B 现有基本能用，补强它（直接编辑现有 SKILL.md）
> - C 确认新建（进入引导式采集 Q1-Q4）

裁决为 C 才进入第一层；A/B 不进入本流程。

**判断不了时**：默认进入第一层（选择题本身能进一步澄清），不阻塞。

**与 E 类（流程串联）的裁决规则**：一句话含多个能力时，看各能力是否有独立产出——各步骤服务于同一最终产出（如"查订单→整理成报告"）归 E 类正常创建；各能力有独立产出（既查又发又通知）判定为范围过大，引导聚焦。

## 第一层：类型定位（4 道选择题）

### 设计意图

这一层的目标是在用户还没组织好语言之前，快速缩窄问题域。4 道题做完后，系统已经能确定：skill 模式类型、输入来源、输出形式、触发场景。

### Q1：你的 skill 主要干什么？

**提问话术：**
> 先告诉我，你想让这个 skill 帮你干什么类型的事情？选最接近的一个：

| ID | 选项文字 | 内部标签 | 推荐模式 | 后续填空模板 |
|----|---------|---------|---------|-------------|
| A | 查数据/排查问题（查日志、查数据库、定位bug） | query_diagnose | P1+P3 | query-template |
| B | 生成内容/代码（建表SQL、代码片段、文档报告） | generate | P1+P5 | generate-template |
| C | 自动化操作（发消息、创建工单、部署上线） | automate | P3+P4 | automate-template |
| D | 数据处理/对账（Excel对比、数据清洗、报表统计） | data_process | P3+P5 | data-process-template |
| E | 流程串联（先做A再做B再做C的多步骤） | orchestrate | P3 | orchestrate-template |
| F | 不确定/以上都不是 | unknown | - | 追问 |

**选 F 的追问策略：**
> "没关系，换个角度问：你平时工作中，哪件重复的事情最让你烦？每次做都觉得'这个应该能自动化'的那种。"

收到回答后，Agent 自行映射到 A-E 中的一个，并回显确认：
> "听起来这属于[X类型]，对吗？"

**防跑偏规则：**
- 如果用户的描述同时涉及 2 个以上类型（如"查数据然后生成报告"），取**最终产出**对应的类型
- 如果实在无法归类，默认走 E（流程串联），后续通过填空题细化

---

### Q2：什么时候会用到它？

**提问话术：**
> 一般什么情况下你会需要用到它？

| ID | 选项文字 | 内部标签 | 对 Skill 的影响 |
|----|---------|---------|----------------|
| A | 有人报了问题/提了需求，我需要处理（被动响应） | reactive | 触发词偏向"问题描述"类（XX报错了、XX异常、查一下XX） |
| B | 我主动想产出某个东西（主动创造） | proactive | 触发词偏向"动作词"类（生成XX、创建XX、写一个XX） |
| C | 定期需要做，每次步骤一样（周期性重复） | periodic | 考虑 automation 集成，触发词含时间词（月报、周检查） |
| D | 偶尔才用，但步骤多容易忘/出错（低频复杂） | complex_rare | 强调 checkpoint 和步骤指引，触发词含流程词 |

**对后续阶段的影响：**
- 选 A → 生成的 description 中触发词侧重问题描述场景
- 选 B → 生成的 description 中触发词侧重动作指令
- 选 C → 在交付时建议配合 automation 使用
- 选 D → 生成的 SKILL.md 中 checkpoint 更密集

---

### Q3：数据/信息从哪来？

**提问话术：**
> 当你用这个 skill 时，它需要的数据或信息从哪里获取？

| ID | 选项文字 | 内部标签 | 对 Skill 的影响 |
|----|---------|---------|----------------|
| A | 我直接告诉它（文字描述、单号、文件路径） | user_input | 输入定义为用户文本；前置检查为参数非空 |
| B | 需要去系统里查（ES、数据库、API、SSH） | system_query | 需 .env.example；需连接前置检查；需安全审计 |
| C | 需要读文件/表格（Excel、JSON、代码文件） | file_read | 输入为文件路径；需文件存在性检查 |
| D | 混合型 / 以上都有 | mixed | 综合处理，按优先级排列输入来源 |

**选 B 时的自动追问：**
> "需要连哪个系统？（可多选）"
> - ES / Elasticsearch
> - MySQL / 数据库
> - Redis
> - SSH 远程服务器
> - HTTP API
> - 其他: ___

这个追问决定了是否需要生成 `.env.example` 以及其中包含哪些变量。

---

### Q4：结果交给谁/怎么呈现？

**提问话术：**
> 做完之后，结果以什么形式给你？

| ID | 选项文字 | 内部标签 | 对 Skill 的影响 |
|----|---------|---------|----------------|
| A | 直接展示给我看就行（终端输出/Markdown） | display | 输出为格式化文本；不涉及文件写入 |
| B | 生成一个文件（SQL/代码/文档/表格） | file_output | 需指定文件格式和命名规则 |
| C | 写回某个系统（数据库/企业 IM/项目管理工具） | system_write | 需写权限；需操作确认；需安全防护 |
| D | 触发下一步操作（发通知/创工单/调接口） | side_effect | 需明确副作用；需操作前确认 |

**选 C/D 时的自动追问：**
> "这个操作执行前需要你确认吗？"
> - 每次都要确认
> - 只在重要/危险操作时确认
> - 完全自动，不需要确认

## 第二层：业务填空（按类型动态生成）

### 设计意图

选择题完成后，根据 Q1 的选择加载对应的填空模板。每个填空题遵循格式：

```
{问题}
  示例："{一个具体的好例子}"
  你的：[___]（可以说"跟示例差不多"来跳过）
```

### 通用填空（所有类型都问）

无论 Q1 选了什么，以下 3 题必问：

**F1 — 给它起个名字**
> 给你的 skill 起个简短的名字（英文，用短横线连接）
> 示例：`order-trace`、`monthly-report`、`table-creator`
> 你的：[___]（没想好可以跳过，我帮你起）

自动起名策略：从"做什么"的描述中提取 2-3 个关键词，kebab-case 拼接。

**F2 — 一句话说明它干什么**
> 用一句话描述：它做什么？（越具体越好）
> 示例："根据中文业务描述，生成符合团队规范的 MySQL 建表 SQL"
> 你的：[___]

如果用户写得太模糊（无动词或无对象），追问：
> "能加上'输入是什么→输出是什么'吗？比如'输入XX，输出YY'"

**F3 — 有没有绝对不能做的事？**
> 有没有这个 skill 绝对不能做的事情？
> 示例："不能生成 DROP TABLE 语句"、"不能修改线上数据库"
> 你的：[___]（没有的话跳过）

### A 类填空：查数据/排查问题

```
A1. 去哪里查？
    → [ES / MySQL / Redis / 日志文件 / 其他: ___]

A2. 用什么条件查？（查询的关键字段）
    示例："订单号"、"配送单号"、"商户ID"、"时间范围"
    你的：[___]

A3. 查到后怎么展示？
    → [表格 / JSON / 按时间线整理 / 摘要一段话 / 其他: ___]

A4. 查不到时怎么办？
    → [提示"未找到" / 换条件重试 / 给排查建议 / 其他: ___]

A5. 需要登录/跳板机吗？
    → [不需要，直连 / 需要 SSH 跳板 / 需要 VPN / 不确定]
```

### B 类填空：生成内容/代码

```
B1. 生成什么格式的内容？
    → [SQL / Go代码 / PHP代码 / Markdown文档 / JSON / 其他: ___]

B2. 有模板或规范要遵循吗？
    → [有（请贴链接或描述） / 参考某个文件 / 没有，自由发挥]

B3. 必须包含什么？
    示例："建表必须有 id、ctime、utime 字段"
    你的：[___]

B4. 绝对不能出现什么？
    示例："不能生成 DROP TABLE"、"不能有中文注释"
    你的：[___]

B5. 生成后需要检查/校验吗？
    → [需要语法检查 / 需要格式校验 / 不需要 / 其他: ___]
```

### C 类填空：自动化操作

```
C1. 操作什么系统？
    → [企业 IM / 项目管理工具 / 数据库 / SSH 远程 / API 接口 / 其他: ___]

C2. 操作前需要确认吗？
    → [每次确认 / 只在危险操作时确认 / 全自动不确认]

C3. 失败了怎么办？
    → [自动重试 / 回滚到操作前 / 停下来报错 / 通知我 / 其他: ___]

C4. 涉及敏感数据吗？
    → [是，需要脱敏 / 否 / 不确定]

C5. 操作有先后顺序要求吗？
    → [有，必须按顺序 / 没有，可以并行 / 部分有顺序]
```

### D 类填空：数据处理/对账

```
D1. 数据源是什么格式？
    → [Excel/CSV / 数据库表 / JSON / API返回 / 多种混合 / 其他: ___]

D2. 处理逻辑是什么？
    示例："对比两份数据的差异"、"按条件筛选后汇总"、"格式转换"
    你的：[___]

D3. 输出什么？
    → [对账差异报告 / 汇总表格 / 清洗后的数据文件 / 统计图表 / 其他: ___]

D4. 数据量大概多大？
    → [几十条 / 几百条 / 几千条 / 上万条 / 不确定]

D5. 异常数据怎么处理？
    → [标记跳过 / 报错停止 / 记录后继续 / 其他: ___]
```

### E 类填空：流程串联

```
E1. 大概有几个步骤？
    → [2-3步 / 4-5步 / 6步以上]

E2. 能简单列一下步骤吗？
    示例："1.查订单信息 2.查配送状态 3.整理成报告"
    你的：[___]

E3. 步骤间有依赖吗？（后一步需要前一步的结果）
    → [是，严格串行 / 部分有依赖 / 没有，可以并行]

E4. 中间某步失败时怎么办？
    → [停下来报错 / 跳过继续下一步 / 重试 / 从头来过]

E5. 需要中间确认吗？（执行到某步时暂停等你确认）
    → [不需要 / 需要（哪步？___）/ 每步都要确认]
```

## 第三层：回显确认

### 设计意图

这是防止"理解偏差"的关键步骤。Agent 把前两层采集到的信息整合成一句人话，让用户判断"你理解得对不对"。

### 回显模板

```
我理解你要的是：

"当{触发场景}时，{从哪里/怎样获取输入}，
 {做什么处理/转换}，
 最终{产出什么形式的结果}。
 如果{异常情况}，则{异常处理}。"

这样对吗？
```

### 确认选项

- **对，继续** → 进入第四层
- **大致对，微调一下：___** → 只修改用户指出的部分
- **不对** → 精准追问（见下方分支）

### 不对时的精准追问

不回到第一题重来，而是定向追问：

> "哪里不对？帮我定位一下：
> A. 触发场景不对（什么时候用它）
> B. 数据来源不对（从哪获取信息）
> C. 处理逻辑不对（做什么事情）
> D. 输出形式不对（结果长什么样）
> E. 异常处理不对（出错时怎么办）"

用户选择后，只重新采集对应部分的信息。

## 第四层：证据采集

### 设计意图

确保生成的 Skill 有"可验证性"——能用真实例子测试对不对。

### 证据 E1：真实使用例子

**提问话术：**
> 给我一个你会怎么使用它的真实例子——就像你平时跟同事说话一样，口语也完全可以。
>
> 示例：
> - "帮我查一下 DD202406150001 这个单子到底卡在哪了"
> - "把这个表的月度数据汇总一下发给我"
> - "根据这段描述帮我建个表"
>
> 你的：[___]

**接受标准：**
- 有具体的对象（单号/文件名/描述内容）
- 是自然语言（不需要格式化）
- 如果用户给的太抽象（如"帮我查数据"），追问："查什么数据？能给个具体的例子吗？"

### 证据 E2：期望输出样本

**提问话术：**
> 如果上面那个例子执行对了，结果大概长什么样？（粗略就行，不需要精确）
>
> 示例：
> - 一段 Markdown 表格，列出订单各节点时间
> - 一段 SQL 代码
> - "在终端输出一个 3 列表格：时间/状态/备注"
>
> 你的：[___]

**接受标准：**
- 能看出输出的格式和关键内容
- 用户说"不确定格式"时 → 追问："至少告诉我，它应该包含哪些信息？"

### 证据 E3：约束来源（可选）

**提问话术：**
> 有没有什么必须遵守的规则或规范？如果有，它来自哪里？
>
> 示例："建表规范来自团队 wiki：必须有 id/ctime/utime，引擎用 InnoDB"
>
> 你的：[___]（没有也可以跳过）

**可选原因：** 很多 skill 没有明文规范，不强制要求但有的话质量更高。

## 防跑偏机制

### 机制 1：范围锁定

一旦 Q1 确定了类型，后续所有问题都在该类型框架内。如果用户在填空阶段说了超出当前类型的需求：

> "这个听起来是另一件事了（属于[X类型]），建议拆成另一个 skill。我们先把当前这个做完，好吗？"

### 机制 2：选择收敛

- Q1 不允许多选。如果用户说"AB都有"，取最终产出对应的类型
- 填空题允许跳过，但通用填空（F1/F2/F3）至少完成 F2

### 机制 3：示例锚定强制

所有填空题必须带示例。Agent 不得展示没有示例的空白问题。如果某类型还没有好的示例，用通用示例兜底。

### 机制 4：超时兜底

如果用户在某个问题上卡住超过 2 轮追问仍无法回答：
- 标记该项为"默认值"
- 使用该类型的通用默认（见 type-templates.md）
- 在最终输出中标注"此项使用默认值，建议后续验证"

### 机制 5：矛盾检测

在回显确认阶段，自动检测逻辑矛盾：
- 输入是"用户直接告诉"但操作需要"系统连接" → 追问：是用户给条件后去系统查吗？
- 输出是"直接展示"但类型是"自动化操作" → 追问：是展示操作结果还是展示操作计划？
- 选了"全自动不确认"但涉及"写回系统" → 提醒：写操作建议至少首次确认

## 信息映射规则

### 选择 → 模式映射

| Q1 | Q2 | Q3 | 推荐模式 |
|----|----|----|---------|
| A(查数据) | any | B(系统) | P1（工具调用：查询封装） |
| A(查数据) | any | A/C | P3（流程：获取输入→查询→整理） |
| B(生成) | B(主动) | A(用户) | P5（护栏：生成+校验） |
| B(生成) | any | C(文件) | P1+P5（读文件→生成→校验） |
| C(操作) | any | any | P3+P4（流程+状态） |
| D(数据) | C(周期) | C/D | P3+P5（流程+护栏） |
| E(串联) | any | any | P3（流程编排） |

### 填空 → 需求规格映射

| 填空项 | 对应需求规格字段 |
|--------|----------------|
